# UML Modeling Document

This document records the current UML material for the laboratory equipment management system. The recommended report figure is the formal UML class diagram below; the later Mermaid diagrams are kept as editable source material for the appendix or future modification.

## Recommended Report Figure

Use these files in the final report:

- `docs/uml-class-diagram-current.svg`
- `docs/uml-class-diagram-current.png`

![Current UML class diagram](uml-class-diagram-current.png)

This is the normal report-facing UML class diagram. It shows:

- class compartments with attributes and selected operations;
- entity classes such as `User`, `Lab`, `Equipment`, `Reservation`, and `Consumable`;
- association classes for many-to-many relationships, such as `StudentLab` and `ReservationConsumable`;
- multiplicities such as `1`, `0..1`, `0..*`, and `1..*`.

The figure is generated by:

```bash
node scripts/generate-uml-class-diagram.js
```

An additional mixed overview figure is available as `docs/uml-overview-current.svg` / `docs/uml-overview-current.png`. It is useful for presentation narration, but the class diagram above is the better choice for the UML section of the report.

## Model Notes

- `WebFrontEnd` is a boundary layer representing the HTML/CSS/JavaScript pages, not a Java class.
- `LabWebServer` is the web boundary class. It registers the API routes, parses form data, checks user permissions, and calls services/DAOs.
- Service classes contain the main business rules and transaction control.
- DAO classes contain SQL queries, joins, and insert/update operations.
- Model classes are simple Java objects used to carry application data.
- The database contains 11 physical tables and 3 SQL views in the current schema.

## Reservation Sequence Source

```mermaid
sequenceDiagram
actor Student
participant UI as Web Front-End
participant API as LabWebServer
participant Service as ReservationService
participant DAO as ReservationDao
participant DB as MySQL Database

Student->>UI: select one linked-lab equipment item, fixed slot, purpose, consumables
UI->>API: POST /api/reservations/create
API->>Service: requestReservation(...)
Service->>DB: begin transaction
Service->>Service: validate fixed slot
Service->>DB: SELECT equipment status FOR UPDATE
Service->>DB: check student_labs access for selected equipment lab
Service->>DAO: hasTimeConflict(...)
DAO->>DB: count overlapping reservations for the equipment
alt slot is free and equipment is available
  Service->>DAO: create reservation
  DAO->>DB: INSERT reservations with equipment_id
  DAO->>DB: INSERT optional reservation_consumables
  Service->>DB: commit
  Service-->>API: reservation id
  API-->>UI: JSON success
  UI-->>Student: show success message
else conflict or unavailable equipment
  Service->>DB: rollback
  Service-->>API: error message
  API-->>UI: JSON error
  UI-->>Student: show error message
end
```

## Maintenance Sequence Source

```mermaid
sequenceDiagram
actor User
actor Technician
participant UI as Web Front-End
participant API as LabWebServer
participant Service as MaintenanceService
participant DAO as MaintenanceDao
participant DB as MySQL Database

User->>UI: report equipment problem
UI->>API: POST /api/maintenance/report
API->>Service: reportProblem(...)
Service->>DB: begin transaction
Service->>DAO: create ticket
DAO->>DB: INSERT maintenance_tickets
Service->>DB: UPDATE equipment SET status='MAINTENANCE'
Service->>DB: commit
API-->>UI: JSON success

Technician->>UI: click accept or repaired action
UI->>API: POST /api/maintenance/update
API->>Service: handleTicketAction(...)
Service->>DB: begin transaction
Service->>DAO: assign(...)
DAO->>DB: UPDATE maintenance_tickets
DAO->>DB: INSERT maintenance_updates
Service->>DB: count active tickets for equipment
alt no active ticket remains
  Service->>DB: UPDATE equipment SET status='AVAILABLE'
else active ticket still exists
  Service->>DB: keep equipment status as MAINTENANCE
end
Service->>DB: commit
API-->>UI: JSON success
```
